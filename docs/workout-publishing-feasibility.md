### Translate the run the athlete approved

The current canonical run records a step purpose, low/nominal/high seconds and RPE, plus ordered repeat blocks. Pace, distance, zone and run/walk examples below are **future inputs**. Synthesize none of them from an E1 RPE target. Garmin documents the builder and FIT features below. Verify partner JSON independently against the approved API. Fix units and compare the fully expanded sequence before delivery. [FI prescriptions][rx] · [Garmin builder][builder] · [FIT step fields][fit]

| Approved intent | Translation and acceptance check |
| --- | --- |
| Easy or long run | Use the running sport and one or more steps with the approved duration or distance. Preserve “easy” or the effort cue. A long run label supplies no pace target. |
| Run/walk, warm-up and cool-down | Keep run and walk as distinct ordered steps with their own end conditions, labels and cues. Preserve warm-up, active, recovery and cool-down roles. Verify the prompt actually tells the athlete when to walk. |
| Repeated work/recovery | Compare expanded step count, order and totals, including the transition into cool-down. For 3 work bouts, between-only recovery expands to W–R–W–R–W. Explicit final recovery expands to W–R–W–R–W–R. FI's current repeat executes every listed step each time. Use explicit steps if the device's skip-last-recover option is unavailable or ambiguous. Check builder/device step limits before expanding. |
| Time or distance | A fixed seconds/metres endpoint can advance automatically. A low/nominal/high window gives the athlete a choice that one timed beep would remove. Preserve the range with an approved lap-button/manual cue where feasible, or obtain approval for a fixed endpoint. |
| Pace range | Preserve both bounds and units. FIT can express a custom speed range. For seconds/km, the slow bound gives the lower speed (1,000 divided by seconds), the fast bound the higher speed. Check display rounding and actual lower/upper alerts on the target watch. |
| HR range or named zone | Preserve explicit bpm bounds as absolute HR. FIT distinguishes bpm, percent of maximum and configured zone numbers. For a named running zone, verify the athlete's running zone system/bounds match the approved reference. A stale or unknown zone mapping blocks zone delivery. |
| Effort only, RPE, instructions | Present the approved effort wording with an open intensity target. A time/distance step may still advance. FIT offers names and notes, and cue display/audio varies with device and setup. Check text length, visibility at the transition and critical instructions. An open target cannot provide a quantitative effort alert. |
| Scheduled date | Retain the athlete-local calendar date and planning time zone, separately from the workout definition. Verify the date in Connect after placement and on the watch after sync. A file creation timestamp has no scheduling meaning. |

If a required target, range, cue or safety limit cannot reach the athlete when needed, mark the translation **blocked** and keep the approved manual prescription available. A display-only cue needs explicit acceptance where it changes execution. A changed training target needs a newly approved canonical revision. The supported manual and partner paths can deliver step-guided runs in principle. End-to-end equivalence for a particular prescription requires device verification. **Lifecycle risks in hevy2garmin.** On changed content the web sync deletes tracked or name-and-marker-matched definitions before creating a replacement, then rebooks future dates. The web library lookup uses one bounded, filtered request (default limit 999), and reconciliation treats absence from that list as missing. Rejecting malformed responses helps, but a valid partial list still proves nothing about deletion. ### Public REST contract

Hevy publishes its current OpenAPI document from its [developer reference][reference]. For personal use, a **valid Hevy Pro personal API key** sent in the `api-key` header authorizes the documented own-account read and write endpoints in principle. No new REST scope is documented for that kind of key. The importer already uses that authentication mechanism and exposes only bounded GET operations for identity, workouts and events. Its successful read path cannot establish current subscription, write entitlement, available capacity or permission to publish this week. Use a separate operation allowlist and credential binding for any future writer. The importer's transport retry loop is designed for reads. [API schema][hr] · [Authentication][ha] · [Hevy help][hh] · [FI read client][client]

| Resource | REST contract and translation consequence |
| --- | --- |
| Routines | `GET /v1/routines` and `GET /v1/routines/{routineId}`. Create with `POST /v1/routines` (201), update by ID with `PUT /v1/routines/{routineId}` (200). Responses document a `routine` object with ID, timestamps, folder and ordered content. Send the full intended body on update. No documented routine DELETE, idempotency key or conditional update in this contract. |
| Folders | `GET /v1/routine_folders`, `GET /v1/routine_folders/{folderId}` and `POST /v1/routine_folders` (201, folder object with numeric ID). Supply the chosen `folder_id` when writing a routine. A multi-routine program requires individual outcomes. The schema lists no folder delete. |
| Exercise identity | List `/v1/exercise_templates` and GET a selected ID for detail. Match exact variant, equipment and tracking units. A custom template can be created with POST to the collection. Require separate authorization for that persistent object. |
| Sets and loads | Ordered sets carry `warmup`, `normal`, `failure` or `dropset`, reps or `rep_range.start/end`, and a single `weight_kg`. Distance in metres, duration in seconds and a custom metric are available for applicable template types. Preserve null versus zero, order, count and equipment-specific load meaning. Map a working set to normal unless a different type was actually prescribed. |
| Rest, supersets and notes | At exercise level the schema accepts `rest_seconds`, `superset_id` and notes. Routine-level notes are accepted on POST/PUT but missing from the documented returned Routine fields. Verify that text independently if essential. Matching superset membership matters more than a particular local group number. |
| Pagination and rate limits | Pages start at one. Routine/folder lists allow ten items per page, exercise templates 100. The published fixed five-minute limits are 1,000 requests per IP and, per account, 40 routine creates, 20 routine updates and 20 folder creates. Account limits are shared with other connected clients. A documented 429 carries an empty body and no Retry-After. Wait out the window on a definitive rejection and revalidate authority before another write. [Rate limits][limits] |

FI's rep targets have low/nominal/high values. Hevy's rep range alone omits the preferred value. FI also supports load ranges, per-group maximum rests, effort cues and RPE ceilings. A single weight, an exercise-wide rest timer and a completed-workout RPE field cannot encode those constraints directly. Show the exact intent in exercise notes where usable (including the preferred reps), identify which cues require the athlete to act, and block if an essential constraint cannot be preserved. Never invent weight, normalize an assisted exercise into added load, or silently collapse a range to its nominal value. [OpenAPI contract][hr] · [FI prescriptions][rx]

### Choosing a Hevy path

| Decision | A · ChatGPT-mediated preview | B · FI as a direct MCP client | C · FI with a REST publisher |
| --- | --- | --- | --- |
| Athlete experience and fidelity | Familiar Save button and full-plan preview. Hand over a minimal deterministic manifest from the approved snapshot. Athlete compares exact exercises, set order and targets before saving. Any edited proposal needs another comparison. | Can pass the same manifest as structured arguments and check the render result. Widget support and callback behavior depend on host. Direct create can bypass the widget only upon explicit instruction. | FI can preview the exact mapped request and diff before dispatch. Gives control of validation, units and warnings. Subject to the same routine field limits. |
| Authority and credentials | Host holds the Hevy OAuth connection. Athlete checks destination and agrees to share the prescription with the chat host. FI cannot infer the host's identity binding from a chat message. | FI handles OAuth lifecycle, token storage, revocation and user/account binding. Confirm that its client can register and support the grant and intended tools. | Single athlete may authorize use of a protected personal key. For an app serving others, use per-athlete OAuth, `modify-routine` (includes routine reads) and `read-exercise`. Store the returned user ID with each grant and serialize refresh-token rotation. |
| Identity, edits and failures | User save remains pending. Associate an exact ID and read back under the bound account, or retain an athlete-reported outcome. Recover one routine at a time. No automatic resubmission on silence. | Direct-create result may provide IDs for folder and children. Persist them and compare the managed content before updating by ID. Preview-to-save has A's receipt gap. No documented all-or-nothing plan save. | Persist per-item returned IDs, read back by ID and compare with the intended content. Keep a shadow copy of last verified fields for edit detection. FI owns ambiguity resolution, stale revisions, partial failures and safe replay. |
| Cost and fit | Smallest single-user handoff. Human comparison and manual reconciliation limit unattended use. Planner can always produce its manifest without MCP. | Adds MCP negotiation, tool/schema drift and potentially widget hosting on top of the same reconciliation work. Consider only if a tested in-app preview materially improves the athlete workflow. | More initial work, but clear operation-level authorization and predictable reconciliation for a standalone app. Pro key generation and OAuth app review/test limits apply. |

Hevy documents up to ten connected accounts during OAuth development, with review before broader release. Its terms address privacy, limited use, competing trackers and AI handling of Hevy data. Evaluate the actual standalone product and data flows when applying. For a preview in chat, send only the approved prescription needed for that session or week. Exclude provider credentials, imported history, health measurements and private rationale. [Hevy developer program][ho] · [OAuth scopes][ha] · [Developer terms][terms]

## Publishing authority and reconciliation

FI persists owner-scoped plans, immutable revision snapshots and approve/decline decisions. The approved head identifies the current revision. Execution observations belong to a separate owner-scoped outcome history. A future publisher consumes these existing records without regenerating workouts from planner inputs. This is an outbound design and requires no changes to E4 or D1. [Plan model][model] · [Approval commands][commands] · [Canonical design][design]

1. **Prepare.** Resolve the authenticated owner, plan, current approved revision, approving decision, logical session and dated occurrence in the planning zone. Bind the destination provider, connection and verified external account ID. A caller-supplied UUID cannot establish ownership. For a revision that moves a session, require its lineage or an explicit old-to-new mapping.
2. **Translate and preview.** Derive a versioned manifest per item from the immutable snapshot. Keep the canonical content digest, translator version, template mappings, unit conversions, destination/folder, exact projected content digest, schedule date and warnings. Classify each field as exact, usable with a disclosed limitation, or blocked. Never let an LLM rewrite the approved snapshot or own a provider ID mapping.
3. **Authorize publication.** Show exactly which operations, items, destination and limitations the athlete would authorize. Record that decision separately from plan approval. Bind it to these digests and a specific operation batch. Re-check the grant, owner, head, future date and execution state immediately before dispatch. If any relevant input changes, expire pending work and preview the new diff. The athlete can use an approved plan without publishing.
4. **Record intent before sending.** Persist a unique local operation and one attempt record per logical item/action. Serialize writes for the same owner, destination and managed item, including retries and competing revisions. Return the stored result for a replay. A local operation ID prevents duplicate local submissions but a provider can still accept a request whose response is lost.
5. **Reconcile at the named destination.** Scope every mapping by FI owner, provider and external account. Record routine/workout ID, folder or calendar-occurrence ID when available, prior verified content, provider revision/timestamp if available and verification method/time. Keep a stable item lineage across plan versions. A title and date help a human locate a candidate but confer no authority to adopt or overwrite it.

| Evidence after dispatch | State and allowable next action |
| --- | --- |
| Preview shown, file written, athlete says they tapped Save | Record preview, export or athlete report at that stage. Verify the account and exact remote record before attaching a provider-confirmed ID. For manual Garmin delivery, record an athlete-observed date/step/device check with its evidence level. |
| Provider returns success and ID | Persist acknowledgement before further calls. Read back mapped content, order, units and parent/date. Mark the verified stage. A Connect readback can confirm calendar placement. Device sync requires an independent watch check or documented acknowledgement. |
| Timeout, connection loss after dispatch, ambiguous server response or crash | Record **unknown**. Suppress automatic create retries, including after worker restart. Use an existing ID, documented provider correlation or an operator-selected item plus account/content verification and explicit confirmation of its origin. Multiple identical candidates, invisible records or uncertain absence keep the outcome unresolved. Retry the original create only when evidence establishes that it failed. If the operator elects to create another item despite unresolved evidence, treat it as a new operation with explicit duplicate-risk acceptance and preserve the first attempt as unknown. |
| Definitive rejection or partial week | Record the reason and each child's result. Retain confirmed items and their IDs. Reconcile unknowns first. Retry only eligible failed items under valid authority. No rollback by deleting a folder or replaying the entire plan. |
| Remote content differs, disappears or moves | Record a conflict. Compare last verified remote content, current remote content and the new approved projection. Present the diff and require a decision to leave it, adopt a mapping or publish an authorized change. Treat an unverified 404, lost permissions or missing listing as insufficient evidence for blind recreation. |

For an approved weekly revision, compare each future occurrence with the last delivered revision. Skip identical items. Amend only FI-managed IDs under the bound account with a clean baseline, including old and new schedule placements. Unschedule an obsolete future occurrence only if the interface supports it and the athlete authorized it. A reusable routine shared by other weeks needs a separate copy or an explicitly reviewed shared update. Protect completed sessions, unrelated calendar entries and user-created routines. Without provider preconditions, pre-read plus post-read detects many conflicts but leaves a race with external edits. Use manual resolution where that risk is unacceptable. Publication failure leaves the approved plan usable. Only the existing execution pathway can establish completion. [FI approval and outcomes][commands]

## Minimal rehearsals and implementation sequence

**Gate for both rehearsals.** Obtain independent review of the exact interface, permitted writes and destination account, followed by explicit operator authorization for the synthetic object, future date, one update, readback and agreed cleanup. Use a test account/environment where the provider offers one. Record only the evidence necessary for reconciliation in private, owner-scoped storage. These are future test plans.

**Hevy · one synthetic routine**

1. Prepare one future slot with one standard barbell bench press, one warm-up set of 5 at 20 kg and two normal sets of 6 at 30 kg. Resolve the exact provider template by name, equipment and weight/reps type, then pin its returned ID before preview. Use a selected destination folder ID or the default folder. Stop if the template is ambiguous. No custom exercise or folder creation is needed.
2. Check the approved version, destination, template ID, order, units and counts in the preview. Authorize a single save. Determine whether this host gives FI a post-click receipt. Otherwise have the athlete identify the newly saved routine and confirm its ID and full structured content via authorized readback. Record any fields verified visually.
3. Approve a new canonical revision changing only the two working sets to 7 reps. Separately authorize the exact update. Read the baseline, update that same routine ID, then read back the new content and confirm the folder and ID remain stable.
4. Replay the same local operation and verify it returns the prior receipt without dispatch. In a local fault simulation, suppress a create response and verify the operation stays unknown. Check scoped before/after IDs for one new routine. A duplicate or conflicting external edit fails the rehearsal. Agree to athlete-led cleanup in Hevy or retention of the synthetic routine. Public REST lacks routine deletion. [MCP workflow][hm] · [REST contract][hr] · [Deletion limits][hh]

**Garmin · one synthetic structured run**

1. Agree on one future local date, zone, consenting account and compatible watch/firmware. Pick the authorized route first. For a calendar rehearsal use manual Connect or an approved Training integration. A file-only test has a narrower pass condition of local watch playback.
2. The fixture consists of a 5 min warm-up, three 2 min work bouts with 1 min walking recovery **between** bouts, then 4 min cool-down. The expanded total is **17 min**, including two recoveries. Preview an open intensity target with the approved effort cue. Verify step prompts, transitions, units and any displayed alert targets on the watch.
3. Authorize one placement and sync. Check the Connect date and exactly one occurrence, then inspect the 955 calendar and workout steps. Capture separate verification of each. Retain the returned workout and schedule IDs if the approved interface exposes them. For manual entry, record the operator's independent observation and its limits. A library listing passes only the device-library check.
4. For one separately approved update, include an explicit 1 min final walking recovery before cool-down, bringing the total to **18 min**. Confirm the intended future occurrence, correct step sequence, no stale or duplicate entry in Connect or on the watch after sync, and no change to another date. Test replay locally and stop on an ambiguous remote result. If authorized, remove only the synthetic calendar occurrence, sync and verify what remains in the workout library. [Calendar controls][calendar] · [955 calendar][watch] · [FIT instructions][fit]

**Recommended order.** Start with an exact manual handoff from an approved snapshot, independent of provider access. Rehearse Hevy preview/save and manual Garmin scheduling separately. Use the results to decide which warnings and receipts are reliable. Implement a narrow Hevy REST publisher only when in-app updating and reconciliation justify it. Evaluate an offline FIT Workout export if the athlete accepts library-only delivery. Put any Garmin cloud adapter after written access confirmation, review of the partner lifecycle contract and a successful calendar/device rehearsal.

**Decisions still open.** The operator chooses whether chat may receive the chosen prescription, which display-only cues are acceptable, whether watch-library delivery is sufficient and whether to send the Garmin inquiry. Ask Hevy whether widget saves expose a supported receipt to external clients, whether plan saves are atomic and whether routine-level notes can be read back. Ask Garmin about the personal eligibility exception, Training-specific evaluation, item/occurrence identity, update/removal and device acknowledgement. Until those answers or rehearsals provide evidence, surface the relevant stage as unverified.
