# B3.3A · Garmin historical synchronization contract

**Decision.** Use an explicitly approved, per-category calendar horizon. January 2025 is a practical candidate for overlap with Hevy. A range limit establishes how much a request can cover. Historical availability, gaps, recording start dates and source changes remain category-specific. Approval for diagnostic samples grants no authority for a backfill.

## Provider contract

The following are documented API capabilities. The bounded evidence section records what was actually tested. The Personal API is scoped to the authenticated user's own data. Keep one verified bearer across the anchor checks and reads, including reads without a profile echo. [Garmin operation schemas](https://developer.garmin.com/gc-developer-program/personal/swagger-docs) · [Personal API FAQ](https://developer.garmin.com/gc-developer-program/personal/personal-faq)

| Feed | Range, identity and time | Ordering, changes and empty results |
| --- | --- | --- |
| Activity search | Inclusive activity-local dates, zero-based offset, default limit 99. Request explicit local-start sort and direction. Parent activities are the default population. Check every owner, ID and local date. | Bare array. No documented span limit, total, stable tie-breaker, snapshot token or modified-since feed. An empty terminal page ends this scan. An exact page multiple needs a further read. |
| Detail / performed workouts | One activity ID per GET. Verify detail's echoed ID and profile. UTC start and provider-local day have separate meanings. Steps use the verified request's activity context. | Detail metadata may supply a UTC last-update time. The workouts response groups ordered steps by index; creation time gives no revision order. Empty workouts array is documented. Detail 404 or a missing activity never authorizes a tombstone. |
| Expenditure, resting HR and intake | Daily summary echoes profile and requested calendar date. V2 wraps dated rows in `data`, supports up to one year, and defines per-row profile, summary source, nested calorie and HR fields. Wellness GMT bounds describe coverage. | No documented pagination, total ordering or comparable revision. V2 consumed kcal is integer. V1 can be fractional. V2 has no documented consumed-data flag. V2 resting HR may fall back to absolute minimum. Preserve those distinctions. |
| Sleep | Daily or range up to 31 days. DailySleepDTO has a profile and sleep calendar date. Preserve GMT sleep bounds including observed epoch-ms precision and overnight spans. | No documented range paging, order or edit cursor. Check row dates, profile and per-metric eligibility. A returned day can lack usable durations. |
| HRV | Daily or range. Published range maximum unspecified. The range wrapper defines a profile and dated overnight/seven-day summaries. Weekly average has no exact observation window. | Both document 204 for no data. Range omits daily chart windows. Row creation time is offsetless and has no documented revision authority. Keep HRV units unverified. |
| Food logs | One user-local day. Match `mealDate`; account scope comes from the verified bearer. Read only daily consumed kcal and evidence required to distinguish a logged zero. Disable media and goals. | No range, paging or edit watermark. Empty meal slots and missing totals cannot establish zero or complete logging. |
| Weight/all | Up to 364 inclusive provider-local days. Use the all-entry array, calendarDate and UTC timestampGMT in milliseconds. No documented stable measurement ID, original writer or device. | No documented pagination, order, revision or deletion marker. Distinct instants may be separate weigh-ins on one day. An empty list describes only the request. |

## Bounded evidence

**Sampled.** Three operator-approved periods used **38 of 40 HTTP attempts**, including key exchange and verification of the original activity and selected feeds. The oldest activity/wellness/weight window fell in the first quarter of the proposed horizon and was more than a year old. Weight used one focus day per period. Daily summary, v2 and food logs were compared on separately selected food days. Two-day activity and wellness windows tested availability without scanning the intervening history. PostgreSQL access was read-only.

| Returned evidence | Recent | Intermediate | Older |
| --- | ---: | ---: | ---: |
| Activity search rows, across two pages of one | 2 | 2 | 2 |
| Detail reads with matching activity/profile, split array and update marker | 1 | 1 | 1 |
| Performed steps in the one requested workout response | 1 | 5 | 1 |
| Sleep rows with duration, both bounds and profile | 2 | 2 | 2 |
| HRV rows with overnight and weekly averages, verified wrapper profile | 2 | 2 | 2 |
| V2 rows with matching profile, distinct local days and Garmin source | 2 | 2 | 2 |
| Eligible daily / v2 / food intake totals on the comparison day | 3, agreed | 3, agreed | 3, agreed |
| Daily expenditure components and total present (of 3) / resting HR present | 3 / yes | 3 / yes | 0 / no |
| Individual API weigh-ins / independent Connect entries | 1 / 1 | 1 / 1 | 1 / 1 |

**Pagination and recovery.** Both offsets returned distinct IDs in the requested descending local-start order in all three windows. Every second page was full, so total window size, terminal-page behavior and stability during edits remain untested. All three detail responses carried a revision marker; detection of an edit to an old activity through search remains unverified. In the recent single-day spot check, sleep duration, stages and both GMT bounds agreed with the range row. Both HRV averages agreed with the daily chart. Range HRV does not establish exact overnight bounds. Empty pages, 204s, deletions and correction sequences were not seen in this diagnostic.

**Intake and expenditure.** The target v2 rows carried a positive consumed value and no consumed-data flag. The corresponding daily totals had the flag set; food totals carried the requested meal date. Expenditure and resting HR agreed between versions on the two comparable days. On the older food day the daily endpoint supplied intake but lacked those recovery fields. There was no paired recovery value to validate there. The three positive day-level comparisons support a range-first intake strategy. They provide no estimate of logging completeness, continuous availability, or the behavior of v2 zeros.

**Weight.** In each period, one dated API entry with a decimal numeric weight and an integer 13-digit GMT millisecond instant corresponded to one independently displayed Connect entry. Exact g-to-kg conversion reproduced all three displayed masses at their recorded precision; interpreting the numbers as kg reproduced none. The recent time matched under the operator-suggested Toronto zone. The two historical references had no supplied zone. Their displayed clocks also matched under a Toronto sensitivity check; this does not independently verify those zones. No sampled row supplied a recognized writer/device/type marker. Differences between underlying devices or measurement types remain untestable from these samples. The local restricted evidence retains the dated displays, units, precision, available clocks, corresponding API numeric forms and instants, and comparison outcomes. Include it in owner erasure and backup expiry.

**Horizon.** Plan to start with the approved portion of the Hevy-era calendar for activity search, sleep, HRV and reported intake; the samples justify attempting it, not marking it covered. Track resting HR and expenditure independently even on days with intake. The three singleton comparisons support proposing grams for the explicitly bracketed weight segment, subject to operator approval, the clock qualification and the exception rules below. Leave earlier/later unverified segments open. Earliest available records, gaps between samples and universal weight-unit consistency remain unresolved.

## Intake and weight decisions

Use v2 as the historical intake primary. Prefer a verified v2 row for a positive reported intake when its day, owner, supplying source and integer kcal are established. Keep its DTO field and retrieval provenance distinct from both B3.2 sources. A v2 zero has no documented intake-presence evidence. Use the daily endpoint to check ambiguous zeros, missing/duplicate dates, differing totals or unverified source labels. Request food logs on independently known logging days with gaps, conflicts, or a small validation sample. If v2 proves unavailable, use one daily GET for intake, expenditure and resting HR together, then the same targeted food-log policy. Never convert an absent feed to zero. Agreement cannot establish full-day logging, an upstream writer or source equivalence. Keep v1 as the resting-HR source until the minimum-value fallback can be distinguished or given its own method.

For weight, authorize a **dated account-and-endpoint segment** with independently displayed entries near its boundaries and, where practical, in its interior. Record source format, tested unit, display precision, time-zone certainty and any positively known device/source transition. Match individual instants at the displayed clock precision and compare both hypotheses with exact g/kg and lb/kg conversion at display precision. Require unique correspondence. Use a bounded segment only when representative checks agree; unbracketed early history remains unverified. Split on conflicting reference results, a new writer/type when actually known, changed time/unit encoding, or anomalous discontinuity. A scale jump can trigger quarantine but cannot pick a unit. Preserve the original numeric observation, documented unit, interpreted unit and verification reference. Seek one targeted additional comparison at the boundary before resuming. No per-weigh-in manual ceremony is needed inside an approved, consistent segment.

## Approximate cost

For a **planning example** of January 2025 through the current investigation (694 days), use 100 weekly activity windows. With page size 10 and two identity scans, listing costs twice the sum of `floor(activities_in_window / 10) + 1`. Add one detail per eligible activity and one optional steps GET per selected activity. Count re-reads if IDs or revisions change. Range cost at 28 days is 25 requests **per feed** for v2, sleep and weight. Seven-day HRV windows add 100. Each single-day fallback or food-log check costs one. Fetch v1 once per day even if several metrics need it.

Illustratively, 200 activities, fewer than ten per week, 50 optional step reads and the four range series cost 625 data GETs before fallbacks. A fresh verified session normally uses one exchange and up to five anchor reads, leaving 34 of 40 attempts. At that capacity the example needs at least 19 sessions and about 739 total requests. A v1 read for all 694 days adds 694 data GETs if v2 is also retained, or 669 net if it replaces v2. Per-day food logs would add another 694. These are workload assumptions, independent of the athlete's activity counts. Size limits, timeouts, retries, nonconvergence and targeted refreshes raise cost. Do not schedule the full example as a rehearsal.

## B3.3B implementation scope

**Backfill.** Extend the trusted local CLI with explicit inclusive dates, feed selection, optional performed steps and a request budget. Verify the original anchor once per bounded session under the account lock. Revalidate and row-lock the active account immediately before each commit. Stage outside the write transaction. Use disjoint 7-day activity windows and initially at most 28 days for eligible range feeds; split a window on response-size or endpoint range limits. Start HRV at seven days as a proposed batch size; only two days were tested. Use the daily chart when actual measurement windows are required. Keep the three-minute, 40-attempt and 2 MB limits. Count exchanges, verification, empty terminal pages, failures and retries. Stop on throttling or loss of authentication; resume through a newly verified session.

**Paging and restarts.** Scan activity windows in ascending local-start order with explicit offset, limit and parent filter. Deduplicate by bound activity ID. Commit verified details, splits and requested steps in restartable units. A page offset is only an in-session hint. Re-scan an interrupted window from offset zero and compare scoped identities across passes before calling the listing complete. Changed ordering, ties, repeated pages or nonconvergence leave it partial; subdivide where possible. For a dense single day, persist pending scoped activity IDs if needed to finish details across invocations; recheck the listing before closure. If even enumeration cannot converge, leave that day partial. Optional steps have their own coverage.

**Incremental refresh.** Refresh from the earlier of the first outstanding day and the start of a configurable seven-day overlap, clamped to the authorized horizon. After downtime, process the gap in bounded chunks. Examine the current provider-local day again on the next run. This is an operating choice, with no guarantee of catching late edits. Provide an explicit older-range refresh for corrections outside the overlap. Hevy's importer serializes a source account, rechecks the binding, commits idempotently and advances its checkpoint only after convergence. Reuse those patterns. Its event cursor, five-minute event overlap and provider deletion events depend on Hevy's contract. Garmin offers no equivalent guarantee. [Hevy importer](../backend/src/fitness_intelligence/adapters/hevy/importer.py) · [Garmin importer](garmin-importer.md)

**Coverage and checkpoint.** Existing `AccountSyncState` has one timestamp per owner/provider/account and cannot distinguish category, local day, partial pages or unresolved weight identity. Keep Hevy's state intact. Add one compact owner/provider/account/category/source-feed/local-day coverage row with attempt time, last successful retrieval, acquisition status, eligible count and options/mapping version. Track intake, expenditure and resting HR separately even when one response supplies all three. Record attempted span where needed to explain a range result. Absence of a row means never queried. Distinguish complete-empty, complete-observed, partial and failed. Record a failed retry separately from the last successful coverage. A validated empty result describes eligible rows returned; it cannot establish athlete behavior. A missing date in a sparse range requires known sparse-response semantics or a single-day confirmation before marking it empty. A 404 on an unverified route is a failed lookup.

Derive the backfill frontier from contiguous completed coverage for the requested feed/options. An explicit skip remains visible as a gap. Keep reconciliation separate from acquisition: an otherwise complete day can contain an unresolved observation. A small scoped issue record needs feed/day, a typed optional activity or instant key, fixed reason, first/last seen and resolution state. Commit observations, issue changes and coverage together. Block or qualify analytics on an open issue even when an older canonical value remains. Omission or an empty retry cannot clear an issue. Resolve only with positive disambiguation or recorded operator review. Keep no health payloads or private free text in coverage and issue records.

**Corrections and replay.** Reject known stale activity snapshots, hold a missing revision after a known one, and reject contradictions between observations established at the same revision. Preserve per-field activity revisions, older positive values through sparse updates and independently retrieved step provenance. Daily recovery corrections take the bounds supported by the accepted value. Intake corrections update only the specific source field and retain evidence on omission. The selector returns at most one total; disagreement remains visible, without averaging or summing. Weight keys are account-scoped exact instants when no upstream ID exists. Preserve distinct instants, quarantine all members of same-instant collisions, and retain the old row with an open issue on a changed mass/unit at an old instant. A disappearing instant plus a new one can mean a retime or a separate event. Preserve both facts, flag a suspected replacement where warranted, and avoid a confident longitudinal count until reconciled. Missing search results, sparse responses and failed detail reads establish no deletion.

**Historical decision replay.** Occurrence time places a fact in the athlete's history. Retrieval/commit time determines when this application could first know it. Mutable latest projections and refreshed retrieval times cannot reconstruct an earlier value or its original availability. Treat historical imports as newly available. Packet 009 decision replay should use the frozen inputs, coverage and mapping versions recorded at the original decision, or mark the replay unavailable. IDs alone cannot freeze mutable content. ## Acceptance and rehearsal

- On disposable PostgreSQL, test owner isolation, lock contention, disconnection before commit, 401/429, response/time limits, atomic rollback, restart after the last committed unit and populated downgrade protection.
- With synthetic DTOs, test page mutation, ties, duplicate IDs, an exact page multiple, empty and capped windows, missing profile/date, sparse range days, incompatible units and changed source shape. Exercise all coverage states and show that a successful retry preserves or resolves prior issues appropriately.
- Test agreeing/conflicting source totals, unconfirmed zero, unavailable food logs, sparse recovery windows, independent step edits, multiple weigh-ins, moved timestamps, unit-segment boundaries and persistent same-instant conflicts. Replay must preserve IDs and create no duplicates. Confirm existing Hevy, Garmin and planning fingerprints.
- After implementation review and explicit write approval, rehearse one small historical segment with independent weight references. Interrupt after one committed unit, resume, then refresh an overlapping window. Audit coverage, unresolved issues, attribution, timestamps, replay counts, privacy and unchanged records. Expand by category only after that audit. Extend encrypted backup, retention, owner erasure and restore/re-erasure to coverage, issue records and private unit evidence.
